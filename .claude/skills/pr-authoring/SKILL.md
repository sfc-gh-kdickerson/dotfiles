# PR Authoring

Turn a branch's diff into a PR title and description that tell a reviewer two things fast: what
changed, and why it changed. Nothing else belongs in the body — no test plan, no AI-attribution
footer.

## Step 1 — Gather the diff

This skill is only about composing the title/description — it doesn't decide what the base branch
should be. Use whatever base is already in play:

- **Existing PR on this branch:** `gh pr view --json number,title,body,url,baseRefName`, then
  `gh pr diff` for the actual diff against that PR's real base. This is the common case when
  refreshing a description.
- **No PR yet:** diff against wherever the branch already tracks/forked from — e.g.
  `git merge-base @{u} HEAD` if there's an upstream, otherwise whatever the branch was created
  from — and `git log`/`git diff` from that point to `HEAD`. Don't assume or hardcode a branch
  name; use what the repo/branch already indicates.

Read the full diff, not just commit messages — commit messages describe intent at the time, the
diff shows what's actually shipping.

## Step 2 — Classify the change

Assign exactly one primary conventional-commit-style type, using the diff content and file paths
as evidence:

| Type | When |
|---|---|
| `feat` | New user-facing capability or behavior |
| `fix` | Bug fix — corrects incorrect behavior |
| `refactor` | Internal restructuring, no behavior change |
| `perf` | Performance improvement, no behavior change |
| `docs` | Documentation only (`*.md`, comments, doc sites) |
| `test` | Tests only, no production code touched |
| `build` | Build system, dependencies, packaging |
| `ci` | CI/CD config (`.github/workflows`, etc.) |
| `chore` | Tooling/config maintenance with no production code impact |
| `style` | Formatting/whitespace only, no logic change |
| `revert` | Reverts a previous change |

If the diff genuinely mixes types (e.g. a `feat` that also touches CI config), pick the type that
represents the PR's *primary intent* — the reason the PR exists — and don't force the rest into
the label. If the mix is large enough that no single type fairly represents it, say so to the user
and suggest splitting the PR rather than picking an arbitrary label.

Also identify a **scope** if one is obvious from the touched paths (e.g. the top-level directory
or module name) — optional, omit if it wouldn't add information.

## Step 3 — Draft the title and body

**Title:** `type(scope): concise summary` (omit `(scope)` if none is obvious). Imperative mood,
lowercase after the colon, no trailing period.

**Body** — exactly two sections, nothing else:

```markdown
## What

- Concrete, specific bullets describing the actual changes — name the files/functions/behaviors
  that changed, not vague restatements of the title.

## Why

- The motivation: the problem this solves, the request that prompted it, or the constraint that
  made it necessary. Pull this from the conversation context, linked issue/ticket, or what the
  diff itself implies if no other context exists.
```

Rules for the body:
- **No Test plan / Testing section.** Ever, even if tests were added — that belongs in the `test`
  bullets under What, not its own section.
- **No "Generated with Claude Code" / "🤖" / Claude attribution line.** This applies to the PR
  title and body only, not to git commit trailers (those follow whatever the repo's commit
  workflow already specifies).
- What is about substance, not narration — don't restate "this PR does X" when a bullet already
  says X.
- Why should explain motivation the diff can't speak for itself — if the reason is genuinely just
  "cleanup" or "the title says it all," a single short line is fine; don't pad it.
- Keep both sections tight. A one-line PR doesn't need five bullets.

## Step 4 — Create or update the PR

No approval pause needed — write it and apply it directly:
- **No existing PR:** push the branch if it has no upstream yet, then
  `gh pr create --title "..." --body "$(cat <<'EOF' ... EOF)"`.
- **Existing PR on this branch:** `gh pr edit <number> --title "..." --body "..."` to replace the
  description.

Report back the title used and the PR URL.

## Important

- Never fabricate a "why" — if the motivation truly isn't recoverable from context, ask the user
  rather than inventing one.
- Don't add a Test plan section even if the user's repo template includes one elsewhere; this
  skill's output is What/Why only, per explicit instruction.
- Base branch selection isn't this skill's concern — it only composes the title/body against
  whatever diff is already in scope (Step 1).
